# 事件增强：依赖、测试在测什么、以及「每事件最多 5 篇」

## 1. 「依赖未安装」是什么意思？

指当前 **Python 环境**里还没有安装 `V3/requirements.txt` 里列出的包（尤其是阶段三用的：`sqlalchemy[asyncio]`、`asyncpg`、`numpy`、`faiss-cpu`、`pyyaml` 以及向量栈等）。  
这不是业务逻辑错误，而是 **环境未就绪**：要么没在该目录执行过 `pip install -r requirements.txt`，要么用了系统自带的旧 `python3`（例如 3.6），装包装到了别的解释器上。

**已在仓库侧约定**：用你本机带到的 Conda / 3.9+ 解释器，在 **`V3/`** 下执行：

```bash
python3 -m pip install -r requirements.txt
```

装好后，阶段三可选 **PostgreSQL**（配置 `EVENT_ENHANCEMENT_DATABASE_URL`）；不配 URL 时为 **JSON 模式**（仍须 `expansion.yaml` 与向量依赖）。

## 2. 「长查询」是什么？为什么以前会很长？

- **长查询**指发给 GDELT DOC 的 HTTP 请求里 `query=` 参数 **特别长**：旧逻辑把 **整段事件标题 + 多篇成员稿标题** 拼成一段 blurb，再用正则抽出很多中英文词，用 **大量 `OR` 子句`** 拼成 `((a) OR (b) OR …) sourcelang:english` 这类字符串。事件标题本身就像一条新闻导语（几十字），再叠成员标题，**OR 核**很容易达到几十到上百个 token，GDELT 侧常返回 **429 Too Many Requests** 或空体。
- **与「事件正文」关系**：真正进 GDELT query 的主要是 **标题类文本**（事件名 + 成员标题），不是 `extracted_text` 全文；但 **事件标题过长** 一样会让抽词变多。
- **当前默认（2026-05-14 起）**：`expansion.yaml` 中 **`gdelt_event_title_max_chars: 15`**（只取事件标题前 15 个 Unicode 字符参与抽词）、**`gdelt_query_include_member_titles: false`**（默认不把成员稿标题拼进 query）、**`gdelt_query_max_or_terms: 4`**（OR 子句上限）。扩搜以 **事件名称（截断）+ `anchor_terms`** 为主，符合「用新闻标题尺度做检索」的口径。详见 `tests/test_gdelt_query_short.py`。

## 4. 「每事件最多 5 篇」与「历史不要删」——当前实现（2026-05-14）

- **配置**：`event_enhancement/config/expansion.yaml` 中 `max_articles_per_event: 5`（可调）。  
- **扩搜入库（PG）**：若该事件在 PG 里 **`event_article_map` 条数已达 5**，本轮 **不再** 插入新扩搜稿（`reason=event_article_cap_reached`），**不执行** `DELETE` 删除已有 `Article` 行。  
- **PG → JSON 合并**：按「当前 `articles.json` 里该 `event_id` 已有条数」计数；若 **已达 5**，则 **不再** 把 PG 里多出来的同事件新 URL 写进 JSON；**不会**从 JSON 里删掉你以前已经存过的行。  
- **若你历史上 JSON 里同一事件已经超过 5 条**：代码 **不会自动删** 以「压到 5」；只是 **停止继续追加** 与 **停止扩搜入库**（直到你人工整理 JSON 或通过别的工具把该事件条数降到 5 以下，扩搜才会再为新稿腾 slot）。若你希望「自动只保留最强 5 条且其余仅解绑不写删」，需要另开需求单做「解绑策略」（仍可不删 `Article` 表行）。

**说明（Docker / GDELT / PG）**：

- **GDELT** 与 Docker、PostgreSQL **无关**；检索模块里的 GDELT 与事件增强里用的是同一类 HTTP 调用。
- 先前「Docker 不可用」仅指 **Cursor 沙箱里未跑 Docker 容器**，不等于你本机不能起 PG；也不表示 GDELT 被关掉。
- **现在**：`EVENT_ENHANCEMENT_DATABASE_URL` **留空** 时走 **JSON 模式**（只读写 `articles.json` / `event_article_map.json`，结果写 `<DATA_DIR>/event_enhancement_last_run.json`），**不必起 PG** 即可完成阶段三代码路径；填写 URL 时仍走原 PostgreSQL 同步与扩搜。

**带 PG 的完整阶段三**：仍可在本机配置 `EVENT_ENHANCEMENT_DATABASE_URL` + Alembic 后使用；与 JSON 模式二选一。
